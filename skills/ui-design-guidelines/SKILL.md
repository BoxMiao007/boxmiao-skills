# 界面设计与实现准则

以下是默认基线:新建组件与样式重写时逐条对照,改动既有元素时顺手修正。它们只描述视觉结果与判据,具体用什么属性、接口或组件由项目所用技术栈决定。项目已有明确规范或用户有明确要求时,以其为准。仅 Web/CSS 项目需要把判据落地成具体写法时,才按需读取 `references/web-implementation.md`(Web 场景的一种实现映射,仅供参考,不是规范条款、也不参与交付核对);其他技术栈无需读取,以免带入无关上下文。

## 一、界面细节规范

1. **等宽数字**:所有会变动的数值使用等宽数字排版,数值变化时宽度不变、不左右抖动;字符本身就等宽的字体天然满足,不必重复处理。
2. **同心圆角**:嵌套元素的外层圆角等于内层圆角加上两者之间的内边距,保证内外弧线视觉同心;从外往内设计时按"内层 = 外层 − 内边距"取内层半径。
3. **标题平衡换行**:标题文字采用平衡换行,让多行标题各行长度均衡,避免最后一行只剩一个词。
4. **柔和阴影替代边框**:卡片与容器的分隔优先用多层柔和阴影,换背景色时阴影自然融合,不必跟着调整边框色;需要保底轮廓时用发丝边,而不是实色细描边。

## 二、前端原则

- **只删"解释界面的文字",不删"界面要展示的内容"**:克制的是次要标签、说明、辅助文案这类解释性文字;告警条目、数据列表、明细、计数、状态等要呈现的内容必须原样保留,不能为了显得简洁就把多条数据概括成一句话、或把列表合并成摘要。判断标准:删掉它,用户是不是就看不到本该看到的信息——是,就不能删。清爽的目标是"没有多余的话",不是"没有内容"。
- 避免不必要的次要标签、说明文字、辅助文案、描述性文字和冗余微文案,让布局、视觉层级、间距和清晰的主操作自己完成解释。
- 优先用强视觉层级和自解释的结构,而不是用文字去解释;默认不添加口号式文字、教学段落,或在每个区块下都加帮助说明。确实需要补充信息时,优先用信息图标加提示气泡,而不是始终显示的次要文字。
- 保留必要的表单标签和可访问名称,界面清爽不能牺牲可访问性。
- 危险或不可逆操作(删除、支付、提交永久性变更)必须保留清晰的后果提示。
- 去掉说明文字后,第一次使用的人仍应能看懂:下一步点哪里、点了会发生什么。
- 重写已有界面时:先去掉冗余标签和说明,如果清晰度下降,再优化布局和按钮文案。

## 交付核对

交付时逐项确认以下结果是否达成,核对的是视觉结果与判据本身,不是具体属性或写法:

- [ ] 所有会变动的数值是否等宽排版,数值变化时宽度不变、不左右抖动(本身等宽的字体除外)
- [ ] 嵌套元素是否满足"外层圆角 = 内层圆角 + 两者之间的内边距",内外弧线同心
- [ ] 多行标题是否平衡换行,末行不会只剩一个词
- [ ] 卡片与容器的分隔是否用柔和阴影,需要保底轮廓时是否为发丝边而非实色细描边
- [ ] 是否去掉了冗余的次要标签、说明文字、辅助文案与微文案,信息是否由结构和视觉层级表达
- [ ] 要展示的内容(条目、列表、明细、计数、状态)是否完整保留,没有被"精简文案"顺带概括、合并或省略
- [ ] 确实需要补充的信息是否用图标加提示气泡按需呈现,而不是始终显示的次要文字
- [ ] 必要的表单标签与可访问名称是否保留
- [ ] 危险或不可逆操作是否保留了清晰的后果提示
- [ ] 去掉说明文字后,首次使用者是否仍能看懂下一步点哪里、点了会发生什么
- [ ] 重写既有界面时,是否先删冗余说明、再按需优化布局与按钮文案
