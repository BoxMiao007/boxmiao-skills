# AGENTS.md 模板(新项目)

初始化时技术栈未定:模板中依赖技术栈的值以"待补全"状态写入,不臆造;开发启动后由 agent 实测回填,回填要求见下表。`{{COMMIT_POLICY}}` / `{{PUSH_POLICY}}` 来自 SKILL.md 第二步与用户确认的策略。语言用简体中文(与用户全局规则一致)。本模板即仓库 `AGENTS.md` 的全部内容(全新项目,无 fork 层)。

用户在 SKILL.md 第二步选择**不发版**时:整段删除「版本与发布」节,删除「完成定义」里那条 CHANGELOG 条目(后续条目编号顺次前移,保持从 1 起连续),且不创建 `CHANGELOG.md`——两处同时写入或同时省略,不留半套规则。

## 回填规则(开发启动后,由当次开发的 agent 执行)

| 待补全处 | 回填要求 |
| -------- | -------- |
| 「项目是什么」 | 用用户描述项目的原话,不改写成技术术语 |
| 「完成定义」第 1 条的验证门命令 | 按"类型检查 + 测试"的组合选命令,逐一实际执行核实后回填;构建/打包命令不算验证门,仅在需要产物时单独执行 |
| 「完成定义」第 2 条的运行方式 | 实际启动核实;纯库/CLI 项目改为"如何调用" |
| 「知识沉淀」第 1 条的依赖安装命令 | 该生态官方命令,如 `uv sync`、`pnpm install`,实测 |
| 「版本与发布」节的版本号载体 | 按生态确定版本号写在哪个文件哪个字段(`package.json` 的 `version`、`pyproject.toml` 的 `project.version`、`Cargo.toml` 的 `package.version`,或独立的 `VERSION` 文件),实测确认后回填,并写入初始版本 `0.1.0` |
| `.gitignore` 技术栈条目 | 按生态补齐 |

## 模板正文

````markdown
# Agent 开发约定

本文件是在本仓库工作的 AI agent 的工作契约。维护者不写代码、只提需求和验收,实现、验证、文档、提交均由 agent 完成。用户全局规则继续生效,本文件只写项目特有约定;两者冲突时,更具体的本文件优先。

## 项目是什么

待补全:开发启动后,由 agent 用用户描述项目的原话补全本节,不改写成技术术语。

## 协作模式

- 用户的话按"需求与验收期望"理解,不是技术指令;技术选型、实现细节、文件组织由 agent 决定。
- 方案不唯一且影响后续走向(技术栈、数据模型、外部服务、付费依赖)时,用简体中文给 2~3 个带取舍的选项让用户选;能安全推断的直接做,做完说明选了什么、为什么。
- 不问只有程序员才能答的技术判断题;确需用户拍板时,一次问清并附默认建议。

## 完成定义(每次交付前逐项核对)

1. 验证门全部通过:验证门命令**待补全**——技术栈确定后,按"类型检查 + 测试"的组合实测回填,没实测过的命令不得写入;回填之前,以第 2 条作为最低标准。
2. 功能实际跑通:能启动的自测核心路径;涉及界面或输出的改动,附截图或运行结果作为交付证据。
3. 向 `CHANGELOG.md` 的 `## [Unreleased]` 追加本次交付的条目:按用户可感知的变化写,一次交付一条,不复述提交列表;破坏性改动在条目行尾标 `（Breaking）`。CHANGELOG 改动跟当次交付一起提交。
4. 交付说明讲给不写代码的人听:做了什么、怎么看到结果(地址/命令/截图)、有什么限制和后续建议;没把握或未完成的部分明说,不藏在细节里。

## 提交与推送

- {{COMMIT_POLICY}}
- {{PUSH_POLICY}}
- 提交信息用 Conventional Commits:`<类型>[(scope)]: <一句话说明>`,类型常用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `ci` / `build` / `chore`,其余类型同样合法。破坏性改动在类型后加 `!`(如 `feat!:`),或在该提交的 footer 里写 `BREAKING CHANGE: <说明>`。这条格式是版本号机械递增的前提,不要随意破例。
- 发布流程里的 `chore(release): vX.Y.Z` 提交属于发布必需动作,不受"不自动提交"限制(见「版本与发布」)。
- 密钥、凭据等敏感内容一律不提交;新增构建产物或本地环境文件类型时,同步补充 `.gitignore`。

## 版本与发布

遵循 SemVer 2.0.0,标签格式 `vX.Y.Z`。首个发布固定为 `0.1.0`,不走区间推导;之后的版本号由上一个 `vX.Y.Z` 标签到 HEAD 之间的全部提交机械决定,取最高优先级:

- 含 `BREAKING CHANGE:` footer,或任意类型带 `!`(如 `feat!:`、`fix!:`、`refactor!:`)→ 升 MAJOR;
- 含 `feat:` → 升 MINOR;
- 其余一律升 PATCH(`fix:`、`perf:`、`docs:`、`chore:`、`test:`、`ci:`、`build:`、`refactor:`);**没写类型前缀的提交也按 PATCH 处理**,不因此停问。

`0.y.z` 阶段:凡按上述规则应升 MAJOR 的,改为升 MINOR,并在 CHANGELOG 对应条目行尾标 `（Breaking）`。这个阶段没有自动出口——只有用户明确说"发正式版"或"进 1.0"时才发 `1.0.0`,该版章节标题行标 `（Breaking）`;agent 不得自行判定功能已稳定而发 `1.0.0`。

区间内提交信息缺失到无法归类、或彼此矛盾时,暂停自动决策:列出候选版本号及理由,请用户选择。

**前置条件(不满足则不进入发布流程)**:验证门全部通过;验证门尚未回填时,以「完成定义」第 2 条(功能实际跑通)作为最低标准,并在发布报告里如实注明验证门未回填。工作区干净——有未提交改动先停下,报告并等指示,不把无关改动塞进发布提交。`## [Unreleased]` 非空——为空时报告"无变更可发布"并停下。

发布步骤(顺序不可颠倒):

1. 更新版本号载体:**待补全**——技术栈确定后,实测确认版本号写在哪个文件哪个字段并回填到本行(如 `package.json` 的 `version`、`pyproject.toml` 的 `project.version`、`Cargo.toml` 的 `package.version`,或独立的 `VERSION` 文件),初始值为 `0.1.0`。
2. 更新 `CHANGELOG.md`:把 `## [Unreleased]` 改成 `## [X.Y.Z] - YYYY-MM-DD`,并在顶部新增空的 `## [Unreleased]`。
3. 提交发布提交:`chore(release): vX.Y.Z`。这次提交只含版本号载体与 CHANGELOG 两处改动。
4. 在该提交上创建本地 annotated tag:`git tag -a vX.Y.Z -m "Release vX.Y.Z"`,**不推送**。建 tag 前先 `git tag -l vX.Y.Z` 检查,同名 tag 已存在时停下报告,不自动覆盖。
5. **停下等用户批准**(闸门规则见用户全局 `AGENTS.md`「发布闸门」)。一次批准覆盖后续全部动作。被驳回或要求改版本号时,保留本地发布提交与 tag,停下询问是改版本号重做还是暂不发布;未经确认不得删除本地 tag 或回退提交。
6. 获批准后推送并建 Release:推当前分支与 tag 到 `origin`,然后 `gh release create vX.Y.Z --title "vX.Y.Z" --notes-file <从 CHANGELOG 提取的对应版本章节>`。Release 正文取 CHANGELOG 该版本章节,不另写一份。

非 GitHub 远程,或环境里没有 `gh`:第 1~4 步照常做,闸门照常停;批准后也无法自动完成第 6 步,此时报告"tag 已在本地创建,推送与发布页需手动完成",把 `git push origin <分支>`、`git push origin vX.Y.Z`、`gh release create` 三条命令原样给出,不静默降级、不假装已发布。推送或 `gh release create` 失败时同样停下,报告失败原因与已推送状态,给出手动命令,不自动重试。

宣称发布完成须附 `git tag -l vX.Y.Z` 与 `gh release view vX.Y.Z` 的实际输出、Release 页面链接,并确认版本号载体与 CHANGELOG 章节一致。已推送的 tag 与已发布版本的 CHANGELOG 章节不可修改。

本节的发布只做 git tag 与 GitHub Release;`npm publish`、`cargo publish` 等包管理器发布不在此列,需要时单独确认。

## 知识沉淀(保证任何新会话都能接手)

- 全新环境的依赖安装命令**待补全**:技术栈确定后实测回填到这里和 README;步骤变化时同步更新。
- 重大技术决策(选型、数据模型、外部服务)在 `docs/decisions.md` 记一行:日期、决策、为什么、放弃了什么。技术栈选型是第一条要记的决策。
- README 面向用户维护:项目是什么、怎么启动、日常怎么用,保持非程序员能看懂。README 不写版本号,当前版本以 CHANGELOG 与 git 标签为准。
````
