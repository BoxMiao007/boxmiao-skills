# AGENTS.md 模板(新项目)

初始化时技术栈未定:模板中依赖技术栈的值以"待补全"状态写入,不臆造;开发启动后由 agent 实测回填,回填要求见下表。`{{COMMIT_POLICY}}` / `{{PUSH_POLICY}}` 来自 SKILL.md 第二步与用户确认的策略。语言用简体中文(与用户全局规则一致)。本模板即仓库 `AGENTS.md` 的全部内容(全新项目,无 fork 层)。

用户在 SKILL.md 第二步选择**不发版**时:整段删除「版本与发布」节,其余内容不变,不留半套规则。

## 回填规则(开发启动后,由当次开发的 agent 执行)

| 待补全处 | 回填要求 |
| -------- | -------- |
| 「项目是什么」 | 用用户描述项目的原话,不改写成技术术语 |
| 「完成定义」第 1 条的验证门命令 | 按"类型检查 + 测试"的组合选命令,逐一实际执行核实后回填;构建/打包命令不算验证门,仅在需要产物时单独执行 |
| 「完成定义」第 2 条的运行方式 | 实际启动核实;纯库/CLI 项目改为"如何调用" |
| 「知识沉淀」第 1 条的依赖安装命令 | 该生态官方命令,如 `uv sync`、`pnpm install`,实测 |
| 「版本与发布」节的版本号载体 | 按生态确定版本号写在哪个文件哪个字段(`package.json` 的 `version`、`pyproject.toml` 的 `project.version`、`Cargo.toml` 的 `package.version`,或独立的 `VERSION` 文件),实测确认后回填;载体有多处时必须同步一致 |
| `.gitignore` 技术栈条目 | 按生态补齐 |

## 项目是什么

待补全:开发启动后,由 agent 用用户描述项目的原话补全本节,不改写成技术术语。

## 协作模式

- 用户的话按"需求与验收期望"理解,不是技术指令;技术选型、实现细节、文件组织由 agent 决定。
- 方案不唯一且影响后续走向(技术栈、数据模型、外部服务、付费依赖)时,用简体中文给 2~3 个带取舍的选项让用户选;能安全推断的直接做,做完说明选了什么、为什么。
- 不问只有程序员才能答的技术判断题;确需用户拍板时,一次问清并附默认建议。

## 完成定义(每次交付前逐项核对)

1. 验证门全部通过:验证门命令**待补全**——技术栈确定后,按"类型检查 + 测试"的组合实测回填,没实测过的命令不得写入;回填之前,以第 2 条作为最低标准。
2. 功能实际跑通:能启动的自测核心路径;涉及界面或输出的改动,附截图或运行结果作为交付证据。
3. 交付说明讲给不写代码的人听:做了什么、怎么看到结果(地址/命令/截图)、有什么限制和后续建议;没把握或未完成的部分明说,不藏在细节里。

## 提交与推送

- 提交信息用 Conventional Commits:`<类型>[(scope)]: <一句话说明>`,类型常用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `ci` / `build` / `chore`,其余类型同样合法。破坏性改动在类型后加 `!`(如 `feat!:`),或在该提交的 footer 里写 `BREAKING CHANGE: <说明>`。这条格式是版本号机械递增的前提,不要随意破例。

## 版本与发布

本项目遵循 SemVer 2.0.0,标签格式 `vX.Y.Z`。递增由当前版本阶段与 Commit 类型机械决定:

- `BREAKING CHANGE:` footer,或任意类型携带 `!`(如 `feat!:`、`fix!:`、`refactor!:`)→ 升 MAJOR;
- `feat:` → 升 MINOR;
- 其余类型一律升 PATCH(如 `fix:`、`perf:`、`docs:`、`refactor:`、`chore:`、`test:`、`ci:`、`build:`);
- 处于 `0.y.z` 阶段时,凡按上述规则应升 MAJOR 的,改为升 MINOR;
- 无法机械判定时,暂停自动决策,列出候选版本号及理由,请用户选择。

递增依据上一个 `vX.Y.Z` 标签到 HEAD 之间的提交;仓库还没有任何 `vX.Y.Z` 标签时,首个发布为 `0.1.0`。

发布流程:

1. 更新承载版本号的文件:**待补全**——技术栈确定后,实测确认版本号写在哪个文件哪个字段并回填到本行(如 `VERSION`、`package.json` 的 `version`、`pyproject.toml` 的 `project.version`);载体有多处时必须同步改成同一个值。
2. 创建本地 annotated tag:`git tag -a vX.Y.Z -m "Release vX.Y.Z"`,**不推送**。
3. 停下并等待用户批准(闸门规则见用户全局 `AGENTS.md`「发布闸门」),报告候选版本号与递增理由。
4. 获批准后推送 tag 并执行 `gh release create`,Release 正文写清本次版本号与变更分类(breaking / feature / fix)。

验证:宣称发布完成须附 `git tag -l vX.Y.Z` 与 `gh release view vX.Y.Z` 实际输出,并确认版本号文件与 tag 一致。已推送的 tag 不可修改。

## 知识沉淀(保证任何新会话都能接手)

- 全新环境的依赖安装命令**待补全**:技术栈确定后实测回填到这里和 README;步骤变化时同步更新。
- 重大技术决策(选型、数据模型、外部服务)在 `docs/decisions.md` 记一行:日期、决策、为什么、放弃了什么。技术栈选型是第一条要记的决策。
- README 面向用户维护:项目是什么、怎么启动、日常怎么用,保持非程序员能看懂。
