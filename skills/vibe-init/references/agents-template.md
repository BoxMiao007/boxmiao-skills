# AGENTS.md 模板(Vibe Coding 新项目)

初始化时技术栈未定:模板中依赖技术栈的值以"待补全"状态写入,不臆造;开发启动后由 agent 实测回填,回填要求见下表。`{{COMMIT_POLICY}}` / `{{PUSH_POLICY}}` 来自 SKILL.md 第二步与用户确认的策略。语言用简体中文(与用户全局规则一致)。本模板即仓库 `AGENTS.md` 的全部内容(全新项目,无 fork 层)。

## 回填规则(开发启动后,由当次开发的 agent 执行)

| 待补全处 | 回填要求 |
| -------- | -------- |
| 「项目是什么」 | 用用户描述项目的原话,不改写成技术术语 |
| 「完成定义」第 1 条的验证门命令 | 按"类型检查 + 测试 + 快速编译"的组合选命令,逐一实际执行核实后回填;完整打包命令不算验证门,仅在需要产物时单独执行 |
| 「完成定义」第 2 条的运行方式 | 实际启动核实;纯库/CLI 项目改为"如何调用" |
| 「知识沉淀」第 1 条的依赖安装命令 | 该生态官方命令,如 `uv sync`、`pnpm install`,实测 |
| `.gitignore` 技术栈条目 | 按生态补齐 |

## 模板正文

````markdown
# Agent 开发约定(Vibe Coding)

本文件是在本仓库工作的 AI agent 的工作契约。维护者不写代码、只提需求和验收,实现、验证、文档、提交均由 agent 完成。用户全局规则继续生效,本文件只写项目特有约定;两者冲突时,更具体的本文件优先。

## 项目是什么

待补全:开发启动后,由 agent 用用户描述项目的原话补全本节,不改写成技术术语。

## 协作模式

- 用户的话按"需求与验收期望"理解,不是技术指令;技术选型、实现细节、文件组织由 agent 决定。
- 方案不唯一且影响后续走向(技术栈、数据模型、外部服务、付费依赖)时,用简体中文给 2~3 个带取舍的选项让用户选;能安全推断的直接做,做完说明选了什么、为什么。
- 需求有歧义且无法从代码、文档或常识推断时,一次问清并附默认建议;不问只有程序员才能答的技术判断题。

## 完成定义(每次交付前逐项核对)

1. 验证门全部通过:验证门命令**待补全**——技术栈确定后,按"类型检查 + 测试 + 快速编译"的组合实测回填,没实测过的命令不得写入;回填之前,以第 2 条作为最低标准。
2. 功能实际跑通:能启动的自测核心路径;涉及界面或输出的改动,附截图或运行结果作为交付证据。
3. 交付说明讲给不写代码的人听:做了什么、怎么看到结果(地址/命令/截图)、有什么限制和后续建议。
4. 未完成或没把握的部分明说,不藏在细节里。

## 提交与推送

- {{COMMIT_POLICY}}
- {{PUSH_POLICY}}
- 密钥、凭据、本地产物(`.env`、`*.pem`、`*.key`、token)不提交;`.gitignore` 保持覆盖。

## 需求与进度

- 一次需求包含多个可独立验证的改动时,先列任务清单再动手,完成一项勾一项,让用户随时看到进度。
- 用户问"现在什么状态"时,答:已完成什么、在做什么、下一步、卡在哪。

## 知识沉淀(保证任何新会话都能接手)

- 全新环境的依赖安装命令**待补全**:技术栈确定后实测回填到这里和 README;步骤变化时同步更新。
- 重大技术决策(选型、数据模型、外部服务)在 `docs/decisions.md` 记一行:日期、决策、为什么、放弃了什么。技术栈选型是第一条要记的决策。
- README 面向用户维护:项目是什么、怎么启动、日常怎么用,保持非程序员能看懂。
````
