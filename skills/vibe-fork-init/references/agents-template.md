# AGENTS.md 模板——协作层

用真实值替换全部 `{{...}}` 占位符后写入目标仓库根目录的 `AGENTS.md`;不适用的小节整段删除,不要留占位符。语言用简体中文(与用户全局规则一致)。所有命令类占位符必须来自 SKILL.md 第一步的收集结果(优先采用 CI 配置里实际在跑的命令),不允许臆造;验证门命令非 CI 来源的按固定格式标注:`命令(待实测:首次运行核实后移除本标注)`;开发首次实际运行核实后移除标注。

本仓库可能是 fork 也可能不是:fork 仓库再按 `fork-agents-sections.md` 追加 fork 层(非 fork 仓库到本文件为止),合并策略见 SKILL.md 第二步 6。

## 占位符对照

| 占位符 | 含义 | 来源 |
| ------ | ---- | ---- |
| `{{PROJECT_SUMMARY}}` | 一句话:这个项目是什么、给谁用 | 项目定位 + 用户想在这个仓库上做的开发,不改写成技术术语 |
| `{{VERIFY_COMMANDS}}` | 验证门命令组合:类型检查 + 测试;构建/打包命令不算验证门,仅在需要产物时单独执行 | 第一步收集到的真实命令;CI 来源直接写,其他来源带"待实测"标注 |
| `{{RUN_COMMAND}}` | 本地运行/启动命令及访问方式 | 从 README/文档提取;纯库/CLI 项目改为"如何调用" |
| `{{COMMIT_POLICY}}` | 提交策略 | 与用户确认过的选项 |
| `{{PUSH_POLICY}}` | 推送策略 | 与用户确认过的选项 |

## 模板正文

````markdown
# Agent 开发约定

本文件是在本仓库工作的 AI agent 的工作契约。维护者不写代码、只提需求和验收,实现、验证、文档、提交均由 agent 完成。用户全局规则继续生效,本文件只写项目特有约定;两者冲突时,更具体的本文件优先。

## 项目是什么

{{PROJECT_SUMMARY}}

## 协作模式

- 用户的话按"需求与验收期望"理解,不是技术指令;技术选型、实现细节、文件组织由 agent 决定。
- 方案不唯一且影响后续走向(技术栈、数据模型、外部服务、付费依赖)时,用简体中文给 2~3 个带取舍的选项让用户选;能安全推断的直接做,做完说明选了什么、为什么。
- 不问只有程序员才能答的技术判断题;确需用户拍板时,一次问清并附默认建议。

## 完成定义(每次交付前逐项核对)

1. 验证门全部通过:{{VERIFY_COMMANDS}}
2. 功能实际跑通:能启动的用 {{RUN_COMMAND}} 启动并自测核心路径;涉及界面或输出的改动,附截图或运行结果作为交付证据。
3. 交付说明讲给不写代码的人听:做了什么、怎么看到结果(地址/命令/截图)、有什么限制和后续建议;没把握或未完成的部分明说,不藏在细节里。

## 提交与推送

- 仓库约定优先:涉及版本、锁文件、发布、提交格式等事项,先查本仓库是否已有明确约定,有则从其约定。
- {{COMMIT_POLICY}}
- {{PUSH_POLICY}}
- 提交粒度:独立功能、缺陷修复或重构分别提交,避免无关改动混入同一个提交;提交前检查暂存内容,确保只含本次任务明确产生且经过检查的改动。
- 密钥、凭据等敏感内容一律不提交;`.env`、`*.pem`、`*.key` 等本地凭据产物,以及新增的构建产物、本地环境文件类型,在第一次提交前先写进 `.gitignore`(不含真实敏感值的 `.env.example` 等样例除外)。发现疑似敏感内容或无法确认安全性时,说明文件路径并停止提交,交由用户决定;不得为完成提交绕过 Git 钩子或其他安全检查。

## 版本与发布

版本号沿用本仓库既有的编号方式(一般即上游约定),本文件不另立编号规则。fork 仓库的编号细则见「发布与版本命名」节。

发布流程:

1. 更新承载版本号的文件(如 `Cargo.toml` 的 `version`、`package.json` 的 `version`);载体有多处时必须同步改成同一个值。
2. 确认版本号改动已在提交中(未提交时先 `git commit -m "chore(release): <标签>"`),再创建本地 annotated tag:`git tag -a <标签> -m "Release <标签>"`,**不推送**。
3. 停下并等待用户批准(发布闸门:未获批准不得推送 tag、不得执行 `gh release create`),报告候选版本号与理由。批准前不再产生新提交;若已产生,批准后先删掉本地 tag 重打(未推送的 tag 可以删),再推送。
4. 获批准后推送 tag 并执行 `gh release create`,Release 正文写清本次版本号与变更内容;`gh` 未认证或仓库无 Release 权限时,只推送 tag 并说明原因,不阻断发布。

验证:宣称发布完成须附 `git tag -l <标签>` 与 `gh release view <标签>` 实际输出,并确认版本号文件与 tag 一致。已推送的 tag 不可修改。

不发布版本的仓库,本节整段删除。

## 知识沉淀(保证任何新会话都能接手)

- 重大技术决策(选型、数据模型、外部服务)在 `docs/decisions.md` 记一行:日期、决策、为什么、放弃了什么。
````
