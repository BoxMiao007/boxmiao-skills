# 既有仓库 Vibe Coding 接管(fork 或非 fork)

把一个已有仓库配置成"用户只提需求,agent 全权实现、验证、交付"的形态;是 fork 再叠加长期同步上游的能力。产出:

- 仓库根 `AGENTS.md`:协作层(协作模式、完成定义、验证门、提交与推送策略、需求登记、知识沉淀);fork 仓库再追加 fork 层(分支模型、上游同步流程、冲突解决规则、功能清单)
- fork 仓库:`upstream` 远程指向源仓库;推送永远只到 `origin`
- 可选:README.md 顶部「AI 开发声明」(fork 仓库追加功能清单块)
- 初始化完成后,日常开发和上游同步不再需要本 skill:按该仓库 `AGENTS.md` 执行

用户不写代码、也不看代码,本 skill 的一切产出以此为设计标准:初始化只跑查询、探测类的快速命令,构建、测试、装依赖这类耗时的留到开发阶段跑;命令收集后如实标注来源与把握程度,交付必须让用户能自己感知结果。

## 第一步:探测现状(只读,不改任何东西)

1. git 状态:远程有哪些、`origin` 指向哪里、当前分支、工作区是否干净。
2. fork 关系:GitHub 仓库用 API 确认 `curl -s https://api.github.com/repos/<owner>/<repo>`(有 `gh` CLI 时用 `gh api repos/<owner>/<repo>`,带认证更稳)——`"fork": true` 时记录源仓库 `"parent.full_name"`、上游 `default_branch`;非 GitHub 平台问用户有没有上游、地址是什么。**fork 与否只决定走哪条分支,不拦截**:非 fork 时跳过 upstream 配置和 fork 层,只做协作层。
3. 本地分支与当前分支;fork 仓库与上游的差距本步不探测——`upstream` 远程多半还没配,留到第三步 1 配好后一并报告。
4. 已有 `AGENTS.md` / `CLAUDE.md`:通读,判断类型:上游维护的(内容面向向上游贡献)、空文件、本仓库自维护的协作约定。已有协作约定的走合并,不覆盖。
5. 构建体系与验证命令。**不按固定清单找文件——枚举永远会漏**(任何生态都可能出现例外)。按信号找:CI 配置里实际跑的命令(最可靠,维护者一直在用)、仓库自己的说明(README、CONTRIBUTING、docs/),锁文件和构建配置只用来判断生态。**初始化只跑查询、探测类的快速命令**(git/gh 查询、读配置文件、查脚本/任务清单等);验证门命令本身(类型检查、测试)和构建、安装依赖、完整打包这类耗时命令不在初始化运行——CI 来源的视为已验证直接采用,其他来源的以"待实测"标注写入,由后续开发 agent 首次使用时实际运行核实后移除标注。两个已知的坑仍要防:引用不存在的命令(仓库没有 `typecheck` 脚本却写 `pnpm typecheck`——写之前核对 package 脚本与 CI 原文)、语义搞错(把"完整打包"当日常验证)。验证门按"类型检查 + 测试"的功能组合选命令,某一类在仓库里确实没有时如实省略,不硬凑;构建/打包命令不属于验证门,仅在需要产物时执行。

## 第二步:与用户确认(每项给默认值,用户一句话采纳)

通用项(所有仓库):

1. **验证门命令**:报出第一步收集到的候选命令及来源(CI 来源直接采用,其他来源标注待实测),让用户过目。
2. **提交策略**(默认):不自动提交——完成并验证后报告,用户说提交才提交(遵循用户全局规则);仅当用户明确要求时,才写入"每个需求验证通过后自动提交"的授权。
3. **推送策略**(默认):不自动推送;用户说"推"才推到 `origin`(上游同步流程的推送也遵循此项)。
4. **README 声明(每次必问,不设默认)**:是否在 README.md 顶部添加;fork 仓库附功能清单块。无论之前在其他仓库怎么选,每次都要问一次。

fork 仓库追加项:

5. **集成分支**:默认沿用当前主分支(通常与上游默认分支同名);仅当用户想要别的名字时改。
6. **AGENTS.md 策略**(按第一步 4 判断的类型给默认):
   - **fork-only(上游维护或无 AGENTS.md 时默认,推荐)**:文件只写本 fork 约定(协作层 + fork 层),头部声明与上游冲突时一律保留本文件版本。上游也维护 AGENTS.md 时必须向用户说明后果:以后每次上游改它都会冲突,按头部规则机械解决(保留 fork 版本)。
   - **合并进自维护内容(已有自维护 AGENTS.md 时默认)**:保留现有协作约定,把 fork 层各节追加进去,语义冲突处(如提交策略)向用户指出后再定。
   - **保留上游内容并追加**:仅当用户明确想同时遵守上游对 agent 的要求时。

## 第三步:执行

1. fork 仓库才做——配 upstream:`git remote -v` 里没有 upstream 才 `git remote add upstream <源仓库>`;已存在则核对指向是否为源仓库,不对时 `git remote set-url` 改正。然后 `git fetch upstream --tags`,报告 ahead/behind 差距。
2. 按 `references/agents-template.md` 写 `AGENTS.md` 协作层;fork 仓库再按 `references/fork-agents-sections.md` 追加 fork 层。占位符全部替换成真实值;验证门命令 CI 来源的直接写,其他来源带"待实测"标注;不适用的段落整段删除,不留占位符。fork 仓库按第二步 6 的策略区分动作:fork-only 与保留上游内容并追加 → 协作层 + fork 层都写;合并进自维护内容 → 现有协作约定不动,只追加缺失的 fork 层各节。非 fork 仓库已有 AGENTS.md 时,不整篇覆盖,只追加缺失的协作层各节,语义冲突处向用户指出后再定。
3. 若用户要 README 声明:按 `references/readme-vibe-declaration.md` 插入。
4. `.gitignore` 按生态补齐:`.env`、`*.key` 等在第一次提交前先写进去。
5. **不自动提交、不推送**:报告全部变更与关键决策(改了哪些文件、AGENTS.md 关键决策),提交时机按确认过的提交策略和用户全局规则。

## 红线

- 初始化只运行查询、探测类的快速命令;构建、测试、安装依赖、完整打包等耗时命令不跑,核实推迟到后续开发首次使用时(与 vibe-init 的"待补全"模式一致)。
- fork 仓库绝不向 `upstream` 推送;推送只到 `origin`。
- fork 仓库不修改上游维护的源码文件;所有约定写进 fork 自己维护的 `AGENTS.md`。
- 模板不复制用户全局规则(语言、依赖管理、破坏性操作确认等全局已有),只写项目特有约定,必要处引用全局规则。
- 初始化只搭框架和规则;功能规划、issue 跟踪、具体功能开发属于后续任务,按写好的 AGENTS.md 执行。
